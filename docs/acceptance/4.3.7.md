## Multi-tab history hold

Hold this candidate update. A later synthetic test mounted two same-account
panels against shared storage and ran their sessions serially. After the
first tab added three events to a 95-record baseline, storage contained 98
records. The second cached tab added three events but again wrote 98 instead
of the expected 101, erasing the first tab's three new events. This reproduced
an inherited write behavior; the 4.3.7 account-scope binding did not introduce
it. The original 95 real history records remain preserved, and no actual user
history loss was observed.

The passing local matrix below remains historical evidence for its checked
scope, not multi-tab acceptance. Version 4.3.8 preparation is tracked in
[acceptance](./4.3.8.md). Installed 4.3.7 activation and a cold read-only history export are now verified;
this does not establish complete tool acceptance. All eight exact-candidate CI checks passed, and the checksum manifest matched
the userscript hash. That historical proof cannot override this known failure. No official release
has been published.

## Presence history

The installed 4.3.6 panel could mount before startup account verification and
remain on Verify account with history controls disabled after the page
identified the current account. No Start or Clear was used on that mount.
The live export retained all 90 prior records plus five new run records, for
95 total; no actual user history loss was observed.

Three synthetic regressions reproduced conditional loss or account mixing
when initial hydration had no verified actor, or later writes followed the
current actor instead of their original scope. The implemented repair lazily
hydrates only a verified nonempty account key and binds each logger and
reviewed run permanently to that scope. Existing render and history controls
refresh visible history without a new polling timer or automatic action.

The 63 focused checks cover unknown-account zero IO, hydration of 90 records,
idle/running account switches, queued and failed writes, late run outcomes,
stale popup controls, explicit Clear continuity and the unchanged 500-entry
bound. The shared history schema, sanitization and write queue are unchanged.
These are component results, not installed 4.3.7 acceptance.

## Native list opening

Installed 4.3.6 cold navigation restored a three-seed Growth draft and its
normal profile links. The next explicit Read current seed attempt stopped
while the newly opened native Followers dialog still had an empty heading.
The app's rendered account rail was behind the modal backdrop, but ordinary
typed-dialog verification could not yet qualify it. No rows were accepted and
no Follow ran; later loaded rows did not complete the stopped attempt.
A later native probe found a typed Following dialog at zero opacity during
its initial fade, while the account rail and header were behind the backdrop.

The implemented opening guard captures fresh account navigation, exact profile
header, route, count controls, restriction and no-existing-dialog proof before
the native click. It rechecks those retained nodes while the single newly
opened dialog loads or fades. Zero opacity is tolerated only on that exact
mounted dialog during opening; hidden ancestors, account controls, unrelated,
extra or replaced dialogs remain refused. Opening text classification uses
rendered text rather than non-rendered SVG icon titles. Default Viewer and
mutation authority remain unchanged.

Opening and initial row readiness share the existing 20-second deadline, with
the outer read deadline retained; Growth keeps its four-minute seed cap.
No rows, result persistence, campaign storage access or action approval are
allowed during the opening phase. Full existing scoped viewer and stored-draft
continuity checks resume before rows, the next list or result persistence.
Stop and account, profile, route, control, dialog or Following-basis drift
stop the read and preserve earlier saved evidence.

The 138 focused checks include 45 new opening cases and existing Viewer,
native-reader and Growth regressions. A delayed native fade/search skeleton
accepts no rows until visible qualification. A heading arriving at 19 seconds
leaves only one second of the shared readiness budget. Seven control-path
checks retain the sole live activator and the two reviewed native-navigation
sites. Both repairs passed independent review.
